## Confirmed algorithm milestone

Scala `app/models/user/time/TimeSpanService.scala` is an eager singleton with a process-local concurrent map `lastUserActivities: userId -> TimeSpan`, initially empty. It does not recover the last span from PostgreSQL. `logUserInteractionIfTheyArePotentialContributor` writes only for the annotation owner or when `annotation.othersMayEdit`; direct `logUserInteraction` has no such gate.

Empty timestamp list logs a warning and succeeds without writes. Otherwise preserve supplied ordering (no sorting). Compare the first timestamp to the user's cached span: gap strictly less than `timeTrackingPause` means continuation (negative gap also counts as continuation). Same annotation continues the span; a switch to another annotation closes the cached old span at the first timestamp, unless that delta is negative, and creates a new zero-duration span for the new annotation. Gap >= pause creates a new span without crediting the idle gap. For each adjacent timestamp pair, if pair gap >= pause, close current span at pair start and create a new span at pair end. Finally close current span at the last timestamp. Any negative update delta is skipped, including its update count; zero delta still increments update count. Cache is updated before database flush. Inserts and updates are prepended, then flushed in list order: newest inserts first, newest planned updates first. This ordering has observable edge cases that must be recorded before implementation.

`TimeSpan.fromInstant` inserts new ObjectId, actual user, Some(annotationId), time=0, numberOfUpdates=0, lastUpdate=created=timestamp, isDeleted=false. `addTime` sets lastUpdate=timestamp, adds duration milliseconds to Long time, and adds 1 to Long numberOfUpdates. DAO inserts all these fields; update writes every field except created. A span update then adds duration to annotations.tracingTime, reloads the annotation under caller access, adds duration to its task's tracingTime when present, and attempts threshold mail. Scala does not wrap the whole multi-table flush in a DB transaction.

## Exact timestamp, ordering and numeric semantics

- Client timestamps are epoch **milliseconds**, not server time. Finish/finishAll bind a required signed Long query `timestamp` and construct `Instant(timestamp)`. Report timestamps use `Instant` JSON: signed Long numbers, epoch-millisecond strings, or ISO instant strings are accepted; output is numeric millis. No clock-skew/future/negative/chronological validation is present in TimeSpanService. Never silently sort, clamp or replace client time with `NOW()`.
- `Instant.-(other)` performs signed Long subtraction first (JVM wrapping), then constructs a millisecond FiniteDuration. Scala 3.8.4 FiniteDuration accepts millisecond length only in [-9_223_372_036_854, +9_223_372_036_854] (approximately 292 years); outside that range constructor throws IllegalArgumentException. `TimeSpan.addTime` time and update-count addition wrap as Long. SQL `COALESCE(tracingTime,0)+delta` uses PostgreSQL BIGINT arithmetic and raises numeric overflow instead of wrapping. These are different boundaries. Representability by SQLx/chrono/PostgreSQL also requires checking before mutating cache; the existing Rust time-reader validates chrono conversion, whereas Scala Instant itself wraps any i64 epoch.
- New span `numberOfUpdates` MUST explicitly start at 0: schema column default is 1, which differs from TimeSpan.fromInstant. Final update at the same creation timestamp increments it to 1 and adds 0 ms. A one-timestamp first request thus persists a zero-duration span, and zero additions change null annotation/task tracingTime to 0.
- The current span remains the previously cached value if a final timestamp would move lastUpdate backward. Example with pause=60000: first report [1000,11000] creates duration10000/count1; overlap [6000,16000] continues old span and adds5000, total15000/count2. Overlap [6000,9000] adds nothing and leaves lastUpdate16000/count2. Each positive/zero *planned span close* increments count once; the number of timestamps is not itself the increment.
- Pause equality is an interruption, not continuation. First report [0,60000] yields two zero-duration spans; [0,10000,70000,80000] yields two10000-ms spans. Start gap>=60000 creates a fresh span and does not close the old one at the new start (no idle-time charge).
- Annotation switching with a short gap charges time until the first new timestamp to the **previous** annotation/task, even if the old span belongs to an annotation now Finished. Switching with a negative gap skips closing the old span and starts a new one at the earlier timestamp. No annotation-state test lives inside the writer.
- Timestamp input is unsorted, including TS reports: AnnotationTransactionService builds timestamps by `updateGroups.map(_.timestamp)`; it does not sort by timestamp in reportUpdates. Internal `sliding(2)` pauses can therefore split a report after earlier overlap. Preserve order and duplicates. Example [0,70000,65000,80000] creates two spans: old span0ms and new span10000ms, not a sorted-series result.
- Flush order is deterministic but reverse-chronological in normal input: insert all newly planned spans in prepend/list order, then update all planned closes in prepend/list order. `Fox.serialCombined` runs sequentially and stops at the first Failure/Empty. There is no sorting by ObjectId or SQL creation time and no direct last-span DB lookup. This matters for which threshold mail occurs first and partial-failure evidence.
- Cache is keyed by user ID alone (across annotations and browser tabs), without TTL, capacity or deletion hooks. Restart clears it; a first post-restart timestamp cannot extend old DB time. TrieMap makes single accesses concurrent-safe but the read/plan/write sequence is not serialized; overlapping requests can race. Cache is written before any insert/update and is not undone on flush failure. A retry after such failure may refer to an unpersisted span or stale absolute totals. This is an existing Scala failure-mode limitation, not a required desirable Rust guarantee.

## Tables, access and flush dependency order

Schema version185 already has all accounting tables; no new table/migration is required for a process-local parity writer.

| Table | Writer operation / dependency |
| --- | --- |
| webknossos.timespans | INSERT _id,_user,_annotation,time,lastUpdate,numberOfUpdates,created,isDeleted; UPDATE same fields except created WHERE _id. No DAO permission check, soft-delete predicate or row-count check in these two methods. _annotation nullable only for legacy data. |
| webknossos.annotations | Per close: global `tracingTime=COALESCE(tracingTime,0)+delta`, without state/soft-delete predicate in UPDATE itself. Then reload through annotations_ with the caller's access context. |
| webknossos.tasks | When reloaded annotation has _task: global `tracingTime=COALESCE(tracingTime,0)+delta`, without state/soft-delete predicate in UPDATE itself. |
| annotations_/tasks_/projects_/users_/multiUsers_ | Live dependencies for reload/threshold mail. Annotation owner, owner MultiUser, task, project, expectedTime, project owner and project-owner MultiUser must all resolve for mail. |

`timespans_` filters isDeleted. Foreign keys: timespans._user -> users ON DELETE CASCADE; _annotation -> annotations ON DELETE SET NULL; both DEFERRABLE. There is no nonnegative time/count CHECK or uniqueness of active spans. Span UPDATE writes absolute accumulated time/count, not a SQL increment. Annotation/task totals are separate atomic SQL increments; they must not be derived by summing only the new annotation's spans because switches close the old annotation too.

Each close in `updateTimeSpanInDb`: (1) derive delta and updated snapshot, (2) update span, (3) update annotation globally, (4) `getAnnotation` reload under supplied DBAccessContext, (5) update task globally if present, (6) best-effort threshold-mail query. Old annotation reload can fail when caller lost read access, even after its global accounting update. TimeSpanDAO mutation bypasses SecuredSQLDAO access checks; annotation/task logTime use GlobalAccessContext (assertUpdateAccess is immediate success). Caller route authentication/restrictions are therefore essential; do not treat an arbitrary requested user/annotation pair as a public accounting endpoint.

Scala does not group these operations transactionally. Each `run` is its own SQL action; a failure can leave inserted spans, updated span totals or annotation totals without task totals. Rust AGENTS.md requires multi-step writes to be transactional: implement all accounting updates for one interaction call in one transaction, with cache publication and mail dispatch after successful commit. Explicitly document this improvement over legacy failure behavior instead of imitating partial corruption. SQL overflow must roll back the complete accounting plan and leave the pre-call cache intact.

## Caller contracts and prerequisite route scope

1. **Annotation info** (already provider/public JSON prerequisites, writer still pending): provide requested annotation, reject Cancelled, compute restrictions and allowAccess, publicWrites first; for authenticated user + supplied timestamp + requested typed enum Task or Explorational, call contributor-gated writer. Then launch lastActivity update and `open_annotation` analytics. Owner or Exclusive/Concurrent qualifies for writer; merely viewing OwnerOnly as admin/manager does not. Sandbox/compound info is not a writer caller. Type aliases/provider actual row behavior still comes from existing provider; the info gate tests parsed requested type.
2. **PATCH /annotations/:typ/:id/finish?timestamp=Long**: provide annotation and restrictions; `allowFinishSoft` requires live owner/task context, owner or manager/admin, and unlocked owner flag but deliberately ignores current Finished state. Active -> server-now modified + state Finished + task compound-cache clear; return task-finished message if _task exists, otherwise annotation-finished. Already Finished -> no state/modified/cache write, annotation-finished message even for Task. Cancelled/Initializing -> notActive failure. Reload provider **before** contributor-gated time writer; final publicWrites consumes that pre-time-write snapshot, so tracingTime in response can be stale compared with committed DB. Writer executes even on repeated Finished success; may add valid remaining interval or count a zero update. It receives the original annotation snapshot and supplied client timestamp. No finish-specific analytics event or email is invoked by this chain.
3. **PATCH /annotations/:typ/finish?timestamp=Long**, JSON `{annotations:[ObjectId...]}`: `Fox.serialCombined` finishes in request order, same timestamp for each ID; stop on first failure, prior successes remain. Duplicate IDs are not deduplicated. This order is also writer annotation-switch order. Preserve per-item success/partial-batch semantics with one transaction per item rather than casually making the whole request all-or-nothing. Shared writer state must persist across items.
4. **PATCH /annotations/:typ/:id/reopen**: **does not invoke the time writer and needs no interaction timestamp**. This can be a separate small lifecycle batch. Resolve annotation/owner, compute admin/task manager, require Finished, require owner or manager/admin, require manager/admin OR `(modified + (features.taskReopenAllowedInSeconds seconds) + 10 seconds).isPast`. Default30s => owner allowed strictly **after40s**, not during the40s; equality fails. The error text says tooLate although source implements minimum waiting time. Do not reverse without an explicit intentional deviation. DAO state Active, clear task compound cache, reload/publicWrites. Modified stays unchanged. No writer cache reset, mail or reopen analytics event in caller. State-trigger pendingInstances behavior comes from schema and must not be manually duplicated: countsAsTaskInstance is typ=Task AND state!=Cancelled AND !isDeleted, so Active<->Finished alone does not change pendingInstances.
5. **POST /tracingstores/:name/handleTracingUpdateReport?key=...**: validated JSON before store-key auth, GlobalAccessContext, annotation read then reject only Finished (`annotation already finished`), update modified using server now. Statistics updates are eagerly launched/silent rather than awaited. Optional userToken lookup is shifted to a Box, so absent/invalid/failed lookup does not reject report or undo modified/statistics. Track interaction only if user resolved AND (significantChangesCount>0 OR !timeTrackingOnlyWithSignificantChanges). Call **unconditionally gated** writer, not owner/contributor-gated writer: tracingstore is trusted to have enforced write access. When resolved user differs from owner, insert contributor `ON CONFLICT DO NOTHING` independently of trackTime and timestamp list. Launch lastActivity update; positive significant/view counts each produce their own analytics event. Empty timestamps still permits contributor/activity/analytics. Cancelled and Initializing are not rejected by this remote Finished-only check.

Remote report DTO source `webknossos-tracingstore/.../TSRemoteWebknossosClient.scala`: annotationId ObjectId, timestamps List[Instant], optional statistics JsObject, significantChangesCount Int, viewChangesCount Int, optional userToken String. Negative counts are accepted by DTO and behave as nonpositive. TS picks last provided group stats and sums group counts as Int (wrapping), forwards timestamps in group order, and calls reportUpdates **before** materializable-version check/actual committed updates. Thus the report is not proof that underlying tracing-engine data committed; avoid inventing all-engine transaction or deduplication claims.

Store-key contract: `TracingStoreService.validateAccess` fetches live tracingStores_ by **key only**, name is only used in denial logging; unknown key returns Forbidden(Msg.TracingStore.notFound). It does not require the named store to equal the key's store or match the annotation dataset. Existing Rust `user_access` and `auth::user_for_service_token` are likely reusable service-boundary precedents; any stricter name/key binding should be explicitly documented, not silently assumed Scala parity.

## Configuration and side effects

Scala conf/application.conf: `webKnossos.user.timeTrackingPause=60 seconds`; `timeTrackingOnlyWithSignificantChanges=false`; `features.taskReopenAllowedInSeconds=30`. `WkConf.scala` reads pause as FiniteDuration, significant gate Boolean, reopen configured Int seconds; AnnotationController adds10seconds once at construction. Writer has no enabled flag and no own periodic timer/flush timer. Rust `Config` currently has mutex expiry but no interaction pause/significant gate fields. Rust `MiscConfig.features` already contains taskReopenAllowedInSeconds30; analytics session_pause30minutes is unrelated and MUST NOT stand in for the timewriter pause.

Threshold mail is per annotation time (not aggregate task time): after accounting, require live owner/MultiUser/task/project/expectedTime/project owner/MultiUser; if `annotation.tracingTime >= expectedTime` AND `annotation.tracingTime - justAddedDelta < expectedTime`, send one overLimitMail to **project owner email**, naming annotation owner (not interacting contributor). expectedTime/tracingTime units milliseconds. Missing expectedTime, optional annotation/task, unavailable live project/user or query failure is swallowed by `.shiftBox`; accounting succeeds. A zero delta cannot cross a normal threshold. Signed threshold subtraction wraps as Scala Long. Multiple racing writers can duplicate threshold mails in Scala; transaction-row serialization plus crossing computation can prevent this in Rust, with callbacks after commit.

Subject exactly `WEBKNOSSOS | Time limit reached. {abbreviatedOwnerName} in {projectName}`; abbreviated name is `(firstName.take(1)+lastName).toLowerCase.replace(" ","_")`, full name firstName + space + lastName. Body names owner/project/task and links `{public_uri}/annotations/Task/{annotationId}`. Source templates: DefaultMails.overLimitMail and views/mail/notifyAdminTimeLimit.scala.html. Mail actor is fire-and-forget; template/config URI/footer source does not affect accounting outcome. Existing Rust `MailSender`/`Mail`/`RecordingMailer` can reproduce subject, recipient and equivalent plain-text link; no over-limit template exists yet and default LogMailer records attempts without delivering SMTP. This transport limitation must remain stated separately from implementing the required dispatch.

Writer itself emits no analytics. Callers emit: info `open_annotation` with annotation_id, annotation_owner_multiuser_id (owner lookup), annotation_dataset_id; remote significant `update_annotation` and view `update_annotation_view_only`, each properties annotation_id and changes_count. Existing Rust analytics::track(AppState,MiscState,AuthUser,event_type,Map) is fire-and-forget and reusable; it stores/forwards events using configured analytics flags and session state. LastActivity uses server-now; Scala caller discards the returned Fox, so failure never rejects response. Rust can deliberately await its local transactional update if documented, while keeping external analytics and mail best-effort after commit.

## Proposed reusable Rust interface (design only)

Introduce a focused `time_interaction` module without a router. Shared `TimeInteractionState(Arc<...>)` is a single extension per assembled app, cloned by all callers; fresh default state per test/router and restart. `TimeInteractionConfig { pause_millis: i64 }` defaults60000, validate positive and within FiniteDuration/chrono arithmetic bounds. The significant-change flag belongs to report-route config, not the algorithm itself. Parent owns additive Config/lib/default constructors/env docs changes. Suggested names (not existing settings): WK_TIME_TRACKING_PAUSE_MILLIS and WK_TIME_TRACKING_ONLY_WITH_SIGNIFICANT_CHANGES. Reopen uses existing features value with checked +10000 milliseconds.

Use a pure planning function `plan_interactions(cached: Option<&SpanSnapshot>, user_id, saved_annotation_id, timestamps: &[i64], pause_millis) -> Result<InteractionPlan, TimeError>`. Plan has ordered inserts, ordered snapshot closes/deltas, and optional next cached span. Capture old annotation IDs in closes. Preserve prepend flush order explicitly; represent signed millis/counts as i64, use explicit wrapping for Scala scalar arithmetic and check FiniteDuration/SQL timestamp conversion before execution. Keep contributor gate as a separate adapter accepting actual owner/collaboration mode; do not bake remote-user restrictions into low-level planner.

For transactional callers, `state.lock_user(user_id).await -> ActivityGuard` acquires an async per-user mutex **before opening transaction/annotation locks**; guard plans using current cached span, then `apply_plan(&mut Transaction<Postgres>, AccessContext, &plan) -> AccountingEffects`. apply inserts/updates spans, global annotation/task totals, and caller-access annotation reload using existing annotation_access::find with explicit `global` flag. It acquires affected annotation/task locks in one documented stable order before execution; SQL task locks should use NO KEY UPDATE because annotation state trigger can also update task pendingInstances. Parent must set common lock-order conventions before finish and remote writers are combined to avoid cross-user annotation-switch deadlocks. No mutex held across remote HTTP calls.

After successful transaction.commit, `guard.publish(plan.next_span)` and `effects.dispatch(MailSender)`; on error/drop cache remains untouched and no mail is sent. Convenient top-level `log_interactions(pool,state,user,annotation,timestamps,access,mailer)` may own its transaction for standalone info, but finish/report should reuse the low-level transaction interface rather than nest transactions. Include a `potential_contributor` wrapper to return a real no-op without opening a transaction when not owner/Exclusive/Concurrent. Empty timestamp input is no-op before cache/SQL locks (warning only). Do not populate cache from SELECT latest timespans: that changes restart semantics.

Recommendations are explicit improvements over Scala: accounting plan atomicity, per-user request serialization, cache publication after commit, consistent resource locking and mail dispatch after commit. Do not hide these behind a parity claim for legacy failure/race behavior. Process-local cache still has no distributed continuation/deduplication guarantee across app instances; avoid schema addition or distributed session ownership in this bounded migration batch. Advisory DB key `time-interaction:<user_id>` can optionally serialize cooperating instances but by itself does not make their independent process caches globally coherent.
